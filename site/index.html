Berkeley weather, and what to wear

Loading the forecast…

How the suggestion works

The forecast comes from the National Weather Service. The suggestion follows these rules, using the next daytime high:

  • 80°F or warmer: T-shirt
  • 68–79°F: light layers
  • 58–67°F: sweater or light jacket
  • 48–57°F: warm jacket
  • Below 48°F: coat, and maybe a hat
  • Rain chance 40% or more: umbrella. 20–39%: a hood, just in case.
  • Wind 15 mph or more: something windproof.
How this is tested

What does this prove?

That a test can follow an API the way a reader follows a guide: one call gives you the address for the next. Many API guides chain calls like this, and that's where docs often go stale, when a response changes shape.

What happens when it runs?

  1. The capture script asks the National Weather Service which forecast covers Berkeley's coordinates. The answer includes the forecast's address.
  2. It fetches the forecast from that address, and saves the next four periods.
  3. Doc Detective makes the first call again and checks that Berkeley's forecast comes from the San Francisco Bay Area office, MTR.
  4. The page turns the next daytime forecast into a clothing suggestion, using the rules under How the suggestion works.

What would make it fail?

Fails the testDoesn't fail the test
The Weather Service stops answering, or answers with an errorRain, wind, or a heat wave: the weather is the data, not the test
The response no longer says Berkeley is covered by the MTR officeA different suggestion from yesterday's
The response changes shape, so gridId is missing

How this is tested

What does this prove?

That a test can check the page itself, not just its data. The German word comes from a list in this repository, so there's no outside source to check. What can break is the page that shows it.

What happens when it runs?

  1. Nothing is fetched: the page picks today's word from german-words.json, based on the date in California.
  2. After the captures run, the site is served on the test machine.
  3. Doc Detective opens it in Chrome, as a visitor would, and checks that every card finished loading, including this word.
  4. It takes a screenshot of the whole page.

What would make it fail?

Fails the testDoesn't fail the test
The page's script breaks, so a card never finishes loadingAnother card's source is down: that card shows its error message, which still counts as finished
A card is renamed or removed without updating the testToday's word is one you've already seen: the list repeats
The word list is empty or isn't valid JSON

NASA's astronomy picture of the day

Loading today's picture…

How this is tested

What does this prove?

That a capture can survive its source failing. NASA's picture of the day API often returns server errors, so the capture falls back to NASA's web page. The test checks the page, because the page is what the card depends on when the API fails.

What happens when it runs?

  1. The capture script asks NASA's API for today's picture, retrying up to three times.
  2. If the API keeps failing, it reads NASA's APOD page instead, and picks the image filed under the current month. The page also shows an unrelated image in its preview tag, so that tag is ignored.
  3. Doc Detective checks that NASA's APOD page answers, retrying twice before it counts a failure.

What would make it fail?

Fails the testDoesn't fail the test
NASA's APOD page doesn't answer, even after two retriesNASA's API fails: the capture uses the page, and this test passes
NASA moves the page without a redirectToday's entry is a video instead of a picture: the card links to it

Where's the test?

{ "checkLink": {
    "url": "https://science.nasa.gov/apod/",
    "statusCodes": [200]
  },
  "onFail": [{ "retry": { "limit": 2, "delay": 3000, "backoff": "exponential" } }]
}

Status of the tools I use

How this is tested

What does this prove?

That a failing test can be good news. These tests fail on purpose when a tool reports a problem, so a red result is the capture doing its job: it shows the day's outage, not a broken page.

What happens when it runs?

  1. The capture script reads the status page of GitHub, Anthropic, and npm, and saves each tool's status.
  2. Doc Detective calls each status page and checks that the tool reports no problems: "indicator": "none".
  3. The card shows a green, amber, or red dot for each tool, and its own description.

What would make it fail?

Fails the testDoesn't fail the test
The tool reports an incident: minor, major, or criticalNothing, unless a tool has a problem: on a normal day, all three pass
The status page doesn't answer

Where's the test?

How this is tested

What does this prove?

That a capture can use a value that changes every run. The search covers the past seven days, so the script works out the start date each morning, rather than storing a fixed date that goes out of date.

What happens when it runs?

  1. The capture script works out the date seven days ago.

Run it yourself

When does it run?

Every morning at 5:23 AM Pacific time (6:23 AM in summer), and whenever I change the site. Anyone can see every run and its test results on GitHub.

How do I run it in my own copy?

Only the repository's owner can start a run in it, so make your own copy:

  1. On the repository, select Fork.
  2. In your fork, open Settings > Pages, and set Source to GitHub Actions.
  3. Open the Actions tab, and turn on workflows if GitHub asks.
  4. Select Capture today > Run workflow.

How do I run it on my computer?

You need Node.js 22 or later and Python 3:

node scripts/capture.mjs
python3 -m http.server 8000 --directory site &
npx doc-detective@4 --config .doc-detective.json \
  --input tests --output results -r terminal -r runFolder
node scripts/results.mjs results

Then open http://localhost:8000.
